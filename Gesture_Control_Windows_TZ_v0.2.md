# Техническое задание
## Система бесконтактного управления компьютером жестами рук через веб-камеру

**Версия документа:** 0.3 (уточнение требований без сокращения функционала)  
**Дата редакции:** 2026-09-17  
**Версии продукта:** MVP v0.1 → MVP v0.2 → v1.0; номер документа не является номером продукта.  
**Целевая платформа MVP:** Windows 10/11  
**Рабочее название:** Gesture Control / Minority-style UI

---

# 1. Идея продукта

Необходимо разработать приложение для Windows, позволяющее управлять компьютером движениями рук и жестами перед обычной веб-камерой.

Система должна:

- определять положение рук;
- отслеживать пальцы;
- распознавать заранее определённые жесты;
- преобразовывать жесты в действия Windows;
- обеспечивать визуальную обратную связь;
- иметь отдельный отключаемый слой анимации в футуристическом стиле.

Ключевая идея:

> Управление должно работать независимо от визуальных эффектов.

Визуализация является дополнительным интерфейсным слоем и может быть полностью отключена.

---

# 2. Основные цели

Главные требования:

1. Управление без специальных перчаток и контроллеров.
2. Работа с обычной веб-камерой.
3. Минимальная задержка между движением руки и действием.
4. Минимум случайных срабатываний.
5. Возможность быстро включать и выключать жестовое управление.
6. Возможность отдельно включать и выключать визуальные эффекты.
7. Поддержка одной и двух рук.
8. Возможность в дальнейшем добавлять собственные жесты.

---

# 3. Архитектурная схема

Основной pipeline:

```text
Camera
  ↓
Hand Tracking
  ↓
Hand Landmarks
  ↓
Gesture Recognition
  ↓
Gesture State Machine
  ↓
Command Engine
  ↓
Windows Input API
```

Параллельно:

```text
Hand Tracking / Gesture State
  ↓
Visual FX Engine
  ↓
Overlay UI
```

Логика управления и графический интерфейс должны быть независимыми модулями.

# 6. Основные режимы приложения

Система должна иметь минимум четыре состояния.

## 6.1 OFF

Камера и распознавание управления отключены.

## 6.2 STANDBY

Камера видит пользователя и руки, но команды Windows не выполняются.

Необходимо для защиты от случайных действий.

## 6.3 ACTIVE

Жесты управляют Windows.

## 6.4 PAUSED

Отслеживание рук продолжается при доступной камере, но команды временно заблокированы. Возобновление допускается только через UI/tray в STANDBY, затем отдельной активацией. Жест не снимает PAUSED. Полная таблица переходов — §67.

---

# 7. Активация управления

Управление не должно автоматически становиться активным только потому, что камера увидела руку.

Для MVP использовать специальный жест активации.

Предлагаемый вариант:

**Открытая ладонь, удерживаемая примерно 0,5–1 секунду.**

После подтверждения:

- появляется визуальный индикатор;
- система переходит в `ACTIVE`.

Повторный жест или отдельный gesture deactivation переводит систему обратно в `STANDBY`.

Точное время удержания должно настраиваться.

# 8. Базовые жесты MVP

## 8.1 Перемещение курсора

Жест:

- указательный палец поднят.

Положение кончика указательного пальца соответствует положению курсора.

Обязательно использовать:

- сглаживание;
- dead zone;
- фильтрацию мелких движений.

Курсор не должен дрожать.

# 9. Рабочая зона руки

Камера не должна требовать движения руки от одного физического края экрана до другого.

Необходимо использовать виртуальную рабочую область.

Например:

```text
центральные 50–70% изображения камеры
                ↓
       100% площади монитора
```

Размер рабочей области должен настраиваться.

---

# 10. Левый клик

Жест:

**Pinch**

Большой и указательный пальцы соединяются.

Подтверждённое замыкание pinch вызывает один `mouse down`, размыкание — один `mouse up`. Завершённый click не отправляется в момент замыкания: это позволяет продолжить тот же жест как drag без предварительного лишнего клика. Подробный контракт приведён в §68.

Обязательно использовать hysteresis.

Пример:

```text
pinch ON  < X
pinch OFF > X + delta
```

Это необходимо для предотвращения многократного случайного клика.

---

# 11. Drag & Drop

Алгоритм:

1. пользователь делает pinch;
2. удерживает pinch;
3. двигает рукой;
4. объект следует за курсором;
5. размыкание пальцев вызывает `mouse up`.

Система должна различать:

```text
pinch + release без существенного перемещения = click
pinch + перемещение за порог = drag до release
```

---

# 12. Правый клик

Предлагаемый жест MVP:

- pinch большого и среднего пальца.

Альтернативный вариант должен быть доступен в настройках.

# 13. Scroll

Первый вариант:

два пальца подняты:

- указательный;
- средний.

Вертикальное движение кисти:

```text
вверх → scroll up
вниз  → scroll down
```

Должен существовать порог движения.

Микродвижения не должны запускать scroll.

# 14. Cancel / Escape

Жест:

- кулак.

Действие:

- `Esc`.

Необходимо предусмотреть минимальное время удержания, чтобы избежать случайного Escape.

# 15. Деактивация

Открытая ладонь с удержанием.

Можно использовать тот же жест, что для активации, но только если система различает состояния `ACTIVE` / `STANDBY`.


# 25. Click FX

При завершённом click из фактической точки курсора расходится короткая окружность. Подтверждённое нажатие pinch отображается индикатором захвата; FX не инициирует ввод.

Пример:

```text
○ → ◎ → ◉
```

Анимация:

- 150–300 мс.

---

# 26. Grab FX

При удержании pinch:

вокруг активной точки появляется:

- замкнутое кольцо;
- дополнительный круг;
- небольшой индикатор состояния `GRAB`.

---

# 27. Palm FX

При обнаружении открытой ладони:

вокруг центра ладони появляется окружность.

Во время активации она постепенно заполняется или замыкается.

Пример:

```text
0% → 25% → 50% → 75% → ACTIVE
```

# 36. Фильтрация координат

Обязательно применить smoothing.

Возможные варианты:

- EMA;
- One Euro Filter;
- Kalman Filter.

`One Euro Filter` является предпочтительным кандидатом для тестирования.

# 37. Защита от случайных жестов

Для каждого gesture должны быть определены применимые параметры:

- enter threshold;
- exit threshold;
- minimum hold time;
- cooldown;
- confidence.

Для непрерывных режимов (курсор, scroll, drag, zoom) cooldown применяется к входу/повторному входу, а не к каждому обновлению. Обязательная выдержка не должна искусственно задерживать движение курсора. Для pinch rearm и cooldown согласуются с double click по §68.

Пример:

```text
GestureDetected
    ↓
Confirming
    ↓
Active
    ↓
Cooldown
```

---

# 38. Gesture State Machine

Не использовать простые условия вида:

```python
if finger_distance < 20:
    click()
```

Необходимо реализовать state machine.

Пример:

```text
IDLE
↓
PINCH_DETECTED
↓
PINCH_CONFIRMED
↓
DRAGGING
↓
RELEASE
↓
COOLDOWN
```

---

# 39. Конфликт жестов

Система должна иметь приоритеты.

Например:

```text
SYSTEM_DISABLE
      ↓
GRAB
      ↓
CLICK
      ↓
CURSOR_MOVE
```

Scroll и click не должны одновременно срабатывать.

---

# 40. Lost Tracking

При потере управляющей руки немедленно прекратить перемещение курсора, scroll и выдачу новых действий. На время `tracking_loss_grace_ms` (по умолчанию 250 мс) сохранить существующий захват, но не экстраполировать движение и не повторять команды.

Возобновление в этот период допустимо только при подтверждении идентичности руки и непрерывности жеста. Иначе освободить ввод и перейти в `PAUSED`.

По истечении grace-периода освободить все кнопки и модификаторы, нажатые приложением, сбросить жесты и перейти в `PAUSED`. При отключении камеры, emergency stop или ошибке input engine grace-период не применяется. Подробности — §67 и §72.

# 41. Calibration

При первом запуске желательно провести короткую калибровку.

Пользователь показывает:

1. руку по центру;
2. руку слева;
3. руку справа;
4. руку сверху;
5. руку снизу.

После этого определяется удобная рабочая область.

Для MVP калибровка может быть ручной.

# 49. Gesture API

```text

```

```text

hand
position
velocity
confidence
duration
state

```

Пример:

```python

    type="PINCH",
    hand="RIGHT",

    confidence=0.94,
```

```text
BACK   ←       HAND       → NEXT

                ↓
              TOOLS
```

Выбор осуществляется направлением пальца + pinch.

# 55. Критерии приёмки MVP

MVP считается работоспособным, если выполняются следующие требования и соответствующие этапу поставки измеримые проверки §73. Этот раздел описывает ожидаемый результат; методика и числовые критерии определены в §73.

## Tracking

Руки стабильно определяются при типичном положении пользователя перед компьютером и нормальном освещении.

## Cursor

Курсор можно переместить в любую часть экрана без заметной дрожи.

## Click

Не менее 95% намеренных pinch должны корректно распознаваться в контролируемом тестовом сценарии.

Один pinch не должен вызывать серию кликов.

## Drag

Объект можно:

- захватить;
- переместить;
- отпустить.

## Scroll

Можно комфортно прокручивать обычную веб-страницу.

## Activation

Управление не начинается случайно только из-за появления руки в кадре.

## Safety

При потере руки drag автоматически завершается.

## Visual FX

`Full / Minimal / Off` переключаются без перезапуска системы распознавания.

## Performance

При отключении Visual FX производительность gesture tracking не должна ухудшаться.

# 59. Первый демонстрационный сценарий

После запуска приложения пользователь включает Gesture Control через UI/tray, переводя приложение из OFF в STANDBY, затем:

1. поднимает ладонь;
2. вокруг ладони появляется синее кольцо;
3. кольцо замыкается;
4. система показывает `ACTIVE`;
5. пользователь вытягивает указательный палец;
6. курсор следует за пальцем;
7. пользователь соединяет большой и указательный пальцы;
8. появляется индикатор нажатия; короткий click ripple показывается после отпускания;
9. пользователь размыкает пальцы — завершается click;
10. для перетаскивания делает новый pinch над объектом и удерживает его;
11. двигает руку за порог drag, переносит объект и размыкает пальцы;
12. два пальца позволяют scroll;
13. swipe переключает окно;
14. пользователь снова удерживает ладонь;
15. система возвращается в `STANDBY`.

Это является целевым demo MVP.

# 67. Нормативная таблица состояний управления

Уточнение dev9, заменяющее привязку к центру из dev8: открытая ладонь остаётся позой управления, но точка курсора по просьбе пользователя возвращена на кончик указательного пальца. Параметр `pointer_mode` задаёт позу/семантику активации, а `pointer_anchor` независимо выбирает INDEX (по умолчанию) или PALM. При одновременном истечении tracking и heartbeat сначала закрывается старая сессия как потеря tracking; после подтверждённой ладони создаётся новая. Реальные ошибки IPC/ввода и ручная аварийная остановка не снимаются автоматически.

Разделы §67–76 конкретизируют предыдущие разделы. Примеры выше не отменяют эти контракты. Все перечисленные функции сохраняются; порядок этапов не разрешает исключать их из проекта.

Уточнение пользователя для dev8: основной режим наведения — открытая ладонь (`pointer_mode=PALM`), координата — сглаженный центр ладони. В этом режиме подтверждённая ладонь включает ACTIVE и восстанавливает управление после потери tracking, но в ACTIVE не переключает в STANDBY, поскольку служит наведению. Pause и аварийная клавиша остаются независимыми командами. Прежнее переключение ладонью и наведение кончиком указательного сохраняются в режиме INDEX; строки ниже о переключении ACTIVE→STANDBY ладонью относятся к INDEX. Для активации PALM допускаются небольшое пространственное дрожание и краткие пропуски классификации, не засчитываемые в выдержку.

| Состояние | Камера и tracking | Команды пользователя в Windows | Выход из состояния |
|---|---|---|---|
| OFF | Отключены, камера освобождена | Запрещены | Enable в UI/tray → STANDBY после успешного запуска камеры |
| STANDBY | Включены | Запрещены | Подтверждённая открытая ладонь → ACTIVE; Disable → OFF |
| ACTIVE | Включены | Разрешены после арбитража жестов | Ладонь → STANDBY; Pause → PAUSED; Disable → OFF |
| PAUSED | Продолжаются, если камера доступна | Запрещены | Resume в UI/tray → STANDBY; только при потере tracking — подтверждённая ладонь → ACTIVE; Disable → OFF |

Начальное состояние — OFF. Автоматическая активация при запуске, восстановлении камеры или появлении руки запрещена. Уточнение пользователя от 17.09.2026: пауза только из-за потери tracking допускает повторный выбор одной руки и возобновление подтверждённой неподвижной открытой ладонью. При этом старый захват освобождён, drag не продолжается, новый pinch требует размыкания. Для аварийной/ручной паузы, ошибки ввода/watchdog, смены камеры/профиля/рабочей области сохраняется ручной Resume и последующая активация. Причина паузы хранится отдельно от состояния PAUSED и не может заменяться потерей tracking во время ручной паузы.

Emergency hotkey из ACTIVE/STANDBY переводит в PAUSED и освобождает ввод; из PAUSED/OFF не включает управление. Название команды в UI — «Аварийная остановка». Отключение с освобождением камеры доступно отдельной командой Disable.

Любой выход из ACTIVE сначала блокирует новые команды, очищает ожидающие команды, освобождает ввод приложения и сбрасывает gesture state. Служебные `mouse up`/`key up` разрешены и вне ACTIVE: запрет касается пользовательских действий, а не очистки ввода.

Открытая ладонь переключает состояние один раз за предъявление. Повторное переключение разрешено только после отсутствия этой позы в течение `activation_rearm_ms`. После перехода в ACTIVE управляющие жесты разрешаются после выхода из позы активации. При входе в ACTIVE уже замкнутый pinch не нажимает кнопку: сначала требуется размыкание.

Pause, Disable и Exit доступны независимо от распознавания. Если регистрацию emergency hotkey выполнить невозможно, приложение показывает причину и остаётся вне ACTIVE до выбора доступной комбинации.

# 68. Единый контракт click, double click и drag

Уточнение dev10: перед подтверждённым pinch наведение фиксируется при раннем сближении пальцев, чтобы сгибание указательного не смещало точку клика. Эта стадия не отправляет down и отменяется при размыкании/таймауте/потере руки. После настоящего down сохраняются обычные правила drag и up. В поставляемом example-конфиге рабочая область установлена на весь кадр; добавлен явный выбор Area 100%.

## 68.1 Левый pinch

Расстояние между кончиками большого и указательного пальцев делится на размер ладони. Размер ладони — расстояние wrist → middle MCP в координатах с одинаковым масштабом осей, например в пикселях кадра. Деление сырых нормализованных x/y без поправки на пропорции кадра не допускается. При слишком маленькой или ненадёжно определённой ладони новые действия блокируются.

`pinch_on_ratio < pinch_off_ratio`; оба порога безразмерные и настраиваемые. Для подтверждения замыкания и размыкания используются отдельные интервалы времени, измеряемые по монотонным timestamps.

Последовательность:

1. В READY рука разомкнута, кнопка отпущена.
2. При входе в порог замыкания начинается CONFIRMING; запоминается точка курсора до сгибания пальцев.
3. После подтверждения выполняется один `mouse down` в точке захвата; состояние PRESSED.
4. Пока смещение меньше `drag_start_distance_dip`, курсор фиксируется в точке захвата. Длительное удержание само по себе не создаёт дополнительные клики и не обязательно означает drag.
5. После превышения порога начинается DRAGGING. Перемещение вычисляется по смещению центра ладони относительно её положения при захвате, с масштабом рабочей области. Это сохраняет управление при согнутом указательном пальце. Переход не должен вызывать скачок курсора.
6. Подтверждённое размыкание выполняет один `mouse up`; если drag не начался, получившаяся пара down/up является одиночным кликом.
7. Перед новым нажатием требуется устойчивое размыкание. Удержание pinch никогда не повторяет `mouse down`.

На выходе из drag курсор сохраняет позицию отпускания. Возврат к управлению указательным пальцем выполняется с временной компенсацией смещения и плавным снятием компенсации, без мгновенного скачка к координате кончика пальца. Параметры перехода задаются в конфигурации.

Событие `LEFT_CLICK` для журналирования и FX означает завершённую пару down/up. Исполнитель не должен повторно вызывать click после уже выполненной пары. Для pinch используются команды `POINTER_DOWN`, `POINTER_MOVE`, `POINTER_UP`; `DRAG_START/END` описывают состояние взаимодействия и не дублируют нажатия.

## 68.2 Правый click

По умолчанию используется pinch большого и среднего пальцев. После подтверждения выполняется правый down, после размыкания — up; курсор фиксируется на время жеста. Правый drag в базовое назначение не входит. Если одновременно подтверждаются левый и правый pinch, новое действие отклоняется до однозначного жеста; существующий захват имеет приоритет.

Альтернатива в настройках — pinch большого и безымянного пальцев. Она выполняет один правый click после подтверждения и размыкания; повтор возможен только после выхода из позы. Альтернативное назначение заменяет исходное, а не запускается параллельно с ним. Ранее предложенное удержание трёх пальцев зарезервировано под вызов экранной клавиатуры дополнением §77; совмещать эти назначения нельзя.

## 68.3 Double click

По умолчанию double click — два завершённых левых pinch без drag, в пределах системного интервала и области двойного клика Windows. Во время ожидания второго pinch действует настраиваемая стабилизация точки клика. Два pinch создают ровно две пары down/up; дополнительный вызов `doubleClick()` не выполняется. Cooldown не должен препятствовать второму pinch в системном интервале.

Также доступно явное назначение `DOUBLE_CLICK` на отдельный поддерживаемый жест; оно создаёт две пары down/up и не совмещается с обычным pinch на том же событии.

# 69. Арбитраж жестов и дополнительные действия

В каждый момент для управляющей руки выбирается один режим взаимодействия. Распознанные кандидаты и причина отклонения журналируются отдельно от выполненных действий.

| Приоритет | Режим или событие | Правило |
|---|---|---|
| 1 | Emergency / Disable / ошибка / потеря tracking | Прервать взаимодействие и освободить ввод по §67, §72 |
| 2 | Подтверждённая деактивация | Завершить текущий ввод, перейти в STANDBY |
| 3 | Уже выполняющийся PRESSED/DRAGGING | Продолжать только захват; блокировать новые click, scroll, swipe, Esc, zoom |
| 4 | Подтверждённый двухручный zoom | Исключительное владение движением; блокировать курсор и scroll |
| 5 | Правый/левый pinch | Выбрать только однозначный кандидат по §68 |
| 6 | Scroll | Зафиксировать курсор; движение руки создаёт только scroll |
| 7 | Swipe / кулак / пользовательский дискретный жест | Одно событие после подтверждения и обязательный rearm |
| 8 | Указательный палец | Перемещение курсора |

До подтверждения кандидата приоритет сам по себе не выполняет команду. Переход между режимами требует выхода из предыдущего жеста; остаточная скорость и накопленный scroll сбрасываются.

Открытая неподвижная ладонь является кандидатом активации/деактивации. Превышение порога скорости сбрасывает hold и допускает проверку swipe. Для swipe задаются минимальные скорость и дистанция, максимальная длительность, допустимое отклонение от горизонтали и rearm после остановки. Уход руки из кадра сам по себе не является swipe.

Кулак отправляет один Esc после выдержки только при отсутствии захвата и другого режима. Сжатие руки во время drag не отправляет Esc; неуверенная поза обрабатывается как потеря достоверности взаимодействия.

Scroll начинается только после подтверждения двух поднятых пальцев. Базовая точка задаётся при входе, величина прокрутки определяется последующим смещением, имеет dead zone, ограничение скорости и накопитель дробных wheel units. Направление прокрутки настраивается. Смена режима обнуляет накопитель.

Swipe вправо по умолчанию выполняет Alt+Tab, влево — Alt+Shift+Tab; все модификаторы освобождаются после каждой команды. Дополнительное назначение — переключение виртуальных рабочих столов. Это разные действия, выбираемые в настройках.

Двухручный zoom требует явного входа: обе закреплённые руки удерживают pinch в течение `zoom_enter_ms`, при этом левый захват ещё не начат. Включённый режим двухручного zoom использует окно арбитража перед одиночным down, чтобы одновременные pinch не создавали предварительный клик. При уже начатом drag zoom запрещён до отпускания. Изменение расстояния между центрами ладоней относительно расстояния при входе управляет Ctrl+wheel. Выход — размыкание любой руки или потеря её tracking. Ctrl не удерживается между отдельными пакетами wheel.

Каждый назначаемый жест имеет одну активную привязку в текущем контексте. Настройки проверяют конфликты и показывают их до сохранения. Запуск приложений использует выбранный исполняемый файл и структурированный список аргументов, без интерпретации командной строки оболочкой по умолчанию. Удержание жеста не запускает несколько копий приложения.

# 70. Идентичность рук, координаты и параметры

`hand_id` — устойчивый идентификатор track; LEFT/RIGHT — отдельная оценка анатомической стороны. Изменение оценки стороны само по себе не заменяет управляющую руку. Сопоставление tracks учитывает положение, непрерывность движения и достоверность; неоднозначность блокирует новые действия.

Пользователь выбирает основную руку: левая, правая или первая активировавшая управление. До явной смены либо повторной активации она закреплена. Появление второй руки не перехватывает курсор. Во время drag замена основной руки запрещена.

Зафиксировать системы координат:

- изображение камеры: пиксели исходного кадра и нормализованные координаты;
- взаимодействие: рабочая область 0..1 после применения выбранной зеркальности;
- экран: физические пиксели целевого дисплея/виртуального рабочего стола;
- UI: DIP с явным преобразованием по DPI монитора.

Зеркальность preview и управления — явные настройки; изменение preview не меняет скрыто управление. Вне рабочей области положение ограничивается границей, а не переносится на противоположный край. При смене разрешения, DPI, камеры или набора мониторов выполняются PAUSED, сброс фильтров и проверка калибровки.

Курсор использует абсолютное отображение рабочей области на дисплей. Настройки «чувствительность/скорость» описывают конкретную кривую отображения и переходные ограничения, сохраняющие достижимость всех краёв экрана; они не являются неопределённым дополнительным множителем координат.

Click ripple и grab ring привязаны к фактической точке курсора. Skeleton и контур руки используют преобразование рабочей области; это условное экранное представление, а не физическое совмещение руки с монитором. Palm status относится к центру ладони. В preview landmarks рисуются в координатах самого кадра.

Параметры имеют единицы, допустимый диапазон и описание: время — мс, скорость руки — доли рабочей области/с, экранные пороги — DIP, pinch — доля размера ладони, scroll — wheel units. Конфигурация валидируется и версионируется; некорректные параметры не применяются молча. Калибровка хранится по камере, разрешению, зеркальности и выбранному дисплею.

Tracking confidence, handedness score и confidence распознавания жеста — разные поля. Если оценка вероятности жеста не калибрована, показывать её как heuristic score, а не как доказанную вероятность правильного действия.

# 71. Runtime, события и производительность

Выбор базового API tracking — MediaPipe Tasks Hand Landmarker; конкретные версии Python, MediaPipe, OpenCV и UI-библиотеки фиксируются после проверки совместимости на целевой Windows. Замена backend допускается через интерфейс perception.

Camera/tracking, interaction/input и UI/FX имеют независимые циклы обработки. Графика получает снимки состояния и не блокирует управление. Разделение на процессы требуется только при подтверждённой необходимости; логическое разделение обязательно.

Для кадров и render state используется ограниченный буфер с предпочтением свежего результата. Не накапливать очередь старых кадров. Все кадры и результаты имеют `frame_id`, монотонный timestamp получения и время завершения inference. Результат старше `max_result_age_ms` (начальное значение 150 мс) не выполняет новые действия и запускает обработку недостоверного tracking. Увеличение этого лимита не отменяет требования к задержке.

Порядок input-команд сохраняется. Устаревшие MOVE можно объединять; DOWN/UP и служебное освобождение нельзя терять из-за переполнения очереди. При перегрузке блокируются новые действия и выполняется очистка ввода. После Pause/Disable команда со старым `session_id` не исполняется, даже если callback пришёл поздно.

GestureEvent дополнительно содержит: `event_id`, `session_id`, `frame_id`, `hand_id`, `phase`, `coordinate_space`, `source_timestamp`, `emitted_timestamp`. CommandEvent содержит ссылку на исходное событие, тип, параметры, идентификатор сессии и срок актуальности. Дискретные события защищены от повторного исполнения.

Отдельно измеряются FPS capture, inference и render, возраст результата, время распознавания, время до отправки input и пропущенные кадры. Интервал подтверждения жеста не включается скрыто в показатель вычислительной задержки.

Отключение FX не перезапускает tracking. Допустимое ухудшение tracking при включении FULL проверяется на референсном ПК; сравнение выполняется с одинаковым входным сценарием и настройками.

# 72. Ошибки, Windows и владение вводом

Input engine ведёт учёт всех кнопок и клавиш, которые нажало приложение. Очистка освобождает именно этот набор; физический ввод пользователя не трактуется как собственное нажатие приложения. Для сочетаний учитывается уже нажатое пользователем состояние модификаторов; конфликтная комбинация отклоняется либо откладывается, без принудительного отпускания физически нажатой клавиши.

Очистка обязательна при Pause, Disable, Exit, потере камеры, истечении tracking grace, ошибке input engine и обрабатываемом исключении. Она должна быть идемпотентной. Логи фиксируют запрос команды и результат отправки отдельно; успешная отправка не доказывает, что целевое приложение выполнило желаемое действие.

Emergency hotkey обрабатывается независимо от inference и UI-анимации. Для восстановления после аварийного завершения основного процесса предусматривается отдельный watchdog, получающий состояние принадлежащего приложению ввода и heartbeat. При пропаже heartbeat он пытается освободить ввод и завершает управляющую сессию. Это не является гарантией при сбое ОС или одновременном завершении всех процессов; такие ограничения явно документируются и не маскируются формулировкой «всегда работает».

При блокировке сеанса или suspend приложение освобождает ввод при получении уведомления и переходит в PAUSED. После unlock/resume, переподключения камеры или перезапуска watchdog требуется явный Resume, затем повторная активация ладонью.

Камера занята, доступ запрещён, устройство отключено и модель не загрузилась — разные диагностические состояния. Автопереподключение допускается с ограниченной частотой, но не возобновляет ACTIVE. Отсутствие камеры не блокирует Settings, tray и Exit.

Базовая среда поддержки — интерактивный пользовательский рабочий стол Windows 10/11 x64 и обычные приложения с тем же или меньшим уровнем целостности. SendInput подчиняется UIPI; управление повышенными окнами из обычного процесса, UAC secure desktop и экраном входа не обещается. Это ограничения платформы, а не исключение жестовых функций. Отдельный режим повышенных прав, если необходим, проектируется явно, без автоматического повышения при запуске.

Overlay не получает фокус, не перехватывает мышь и клавиатуру, не влияет на порядок input-команд. Проверить работу при разных DPI и конфигурациях дисплеев, а также документировать поведение поверх полноэкранных приложений. Настройки открываются отдельным обычным окном.

# 73. Воспроизводимая приёмка

Числа ниже — первоначальные целевые критерии, а не утверждения о достигнутых характеристиках. Их изменение требует явной редакции ТЗ и обоснования результатами измерений; нельзя объявлять выполнение по субъективному впечатлению.

До оценки производительности составляется паспорт референсного стенда: CPU/GPU/RAM, сборка Windows, версия драйвера камеры, разрешение и FPS захвата, дисплей и DPI, версии зависимостей, режим питания. Базовый сценарий: камера 640×480 при 30 FPS, расстояние 0,5–0,9 м, равномерное освещение 300–700 лк без сильного контрового света. Дополнительно проверить слабый свет, частичное перекрытие пальцев, выход за кадр и быстрое движение; допустим отказ от действия, но не незапланированный ввод.

| Проверка | Сценарий и критерий |
|---|---|
| Click | Не менее 100 намеренных pinch на каждого из минимум 3 пользователей; ≥95% дают ровно один клик по нужной цели; отдельно считать пропуски, дубли и неверные цели |
| Ложные действия | Для каждого пользователя 30 минут обычных движений в STANDBY: 0 активаций и 0 пользовательских input-команд; 30 минут ACTIVE без намеренных команд: 0 ложных click, drag, Esc, swipe и запусков приложений |
| Double click | 30 попыток на пользователя в системном интервале; ≥90% успешных открытий тестовой цели, без третьего клика |
| Правый click | 30 попыток для каждого доступного способа; ≥95% корректных вызовов контекстного меню, без левого клика |
| Drag | 30 переносов в цели на разных участках экрана; ≥95% успешных; после завершения 0 принадлежащих приложению зажатых кнопок |
| Дрожание | Неподвижная рука 10 с в каждой из 5 точек; 95% положений курсора в радиусе 5 DIP от медианы; отдельно выполнить повтор на записанных landmarks для оценки фильтра |
| Достижимость | Доступны все углы и края выбранного дисплея; после переключения режима нет скачка свыше 10 DIP при неподвижной руке |
| Scroll | 20 входов/выходов; при неподвижной руке 0 scroll за 10 с; прокрутка в обе стороны без click и движения курсора |
| Активация | 30 циклов; одно удержание ладони даёт ровно один переход; ещё 5 с удержания не переключают состояние повторно |
| Emergency | 20 остановок, включая drag, zoom и нагрузку FULL; блокировка новых команд и запрос освобождения ввода не позднее 100 мс после получения hotkey приложением |
| Потеря tracking | 20 исчезновений во время drag; нет нового движения после обнаружения потери; освобождение не позднее grace + 100 мс; возврат руки не возобновляет завершённый drag |
| Зависание/авария | Искусственно остановить heartbeat и завершить основной процесс; watchdog запрашивает освобождение не позднее 500 мс после последнего heartbeat; выполнить по 10 повторов |
| Производительность | За 10 минут tracking в среднем ≥30 FPS при достаточном FPS камеры; ни одно устойчивое 10-секундное окно ниже 20 FPS на референсном стенде; CPU/RAM фиксируются в отчёте |
| Задержка | Цель camera→cursor: p95 ≤80 мс, стремиться к медиане ≤50 мс; публиковать медиану/p95 и метод измерения отдельно для FULL/MINIMAL/OFF |
| Независимость FX | 30 переключений FULL/MINIMAL/OFF без перезапуска tracking, потери захвата или повторных команд; OFF не ухудшает FPS и p95 latency больше чем на 5% с учётом повторных замеров |
| Zoom и две руки | 20 входов/выходов и 20 пересечений рук; нет предварительного левого клика, перехвата курсора или оставленного Ctrl; масштаб меняется в обе стороны |
| Multi-monitor | Два дисплея с разным DPI, включая дисплей с отрицательными координатами; проверить выбор, переходы, общую область и безопасное отключение дисплея |
| Назначения | Для каждой команды клавиши, сочетания, запуска приложения и рабочего стола — 20 повторов; одно подтверждение вызывает одно действие, удержание не повторяет его |

Программные timestamps обычно измеряют путь от получения кадра, а не от физического движения до изображения курсора. Полную camera→cursor задержку проверять внешней видеозаписью/высокоскоростной съёмкой; не выдавать время inference за end-to-end latency. Видео для такого теста записывается только при явно включённом диагностическом режиме и согласии участника, с указанным местом хранения и удалением.

Автоматические тесты state machine используют синтетические landmarks и управляемые часы: дрожание порогов, drop frames, поздний callback, повтор события, конфликт жестов, выход из ACTIVE и восстановление. Интеграционные проверки используют подменный input backend; реальные действия Windows проверяются отдельно в тестовой среде. Нулевая частота ошибок в ограниченном сценарии не является обещанием отсутствия ошибок при любых условиях.

# 75. Поставка, настройки и приватность

Результат каждого этапа поставки: исходники, зафиксированные зависимости, воспроизводимая инструкция сборки, запускаемый Windows x64 пакет без отдельно установленного Python, пример конфигурации, описание жестов, ограничения и отчёт приёмки. Формат первой поставки — portable ZIP; установщик допускается дополнительно. ARM64 не заявляется без отдельной проверки совместимости.

Модель tracking и необходимые runtime-ресурсы включены в пакет; запуск и управление не требуют сети. В поставке присутствуют сведения о версиях и лицензиях компонентов. Сборка проверяется на чистой целевой Windows без среды разработки.

Настройки хранятся в пользовательском каталоге приложения, записываются атомарно, имеют `schema_version`, миграцию и резервную копию последней корректной версии. При повреждении файла используются безопасные значения, управление остаётся OFF и показывается сообщение. Предусмотреть сброс настроек и калибровки.

Видео, изображения и последовательности landmarks не сохраняются по умолчанию. Debug log содержит события, причины решений, агрегированные метрики и ошибки; имеет ротацию и ограничение размера. Запись диагностического набора включается отдельно, с явным указанием состава, расположения и способа удаления. Облачные функции отсутствуют в текущей поставке.

# 78. Уточнение двухручного управления и жестов Windows — dev26

По согласованию с пользователем двухручное управление включается отдельной опцией `second_hand_enabled` (по умолчанию выключено). Основная рука сохраняет системный курсор и синюю руну; вторая имеет красную руну-индикатор. Два независимых системных курсора не создаются. Начальная активация и восстановление после полной потери основной руки выполняются одной открытой ладонью.

Два почти одновременных щипка с подтверждением 250 мс включают Ctrl+wheel Zoom. При наличии второй руки окно арбитража одиночного щипка составляет 200 мс. Уже начатый захват приоритетнее Zoom. Потеря второй руки, неоднозначность пары или размыкание щипка завершают Zoom без переноса удержания в обычный левый клик. Ctrl не удерживается между пакетами wheel.

Добавлены отключаемые жесты четырёх поднятых пальцев с подогнутым к ладони большим: вертикальное движение вверх — Win+Tab (обзор приложений и рабочих столов), вниз — Win+D (показать/вернуть рабочий стол). Это дополнение не заменяет переключение приложений смахиванием кисти. Порог движения и скорости конфигурируемые. Отдельное переключение между виртуальными рабочими столами остаётся самостоятельным пунктом исходного объёма.
